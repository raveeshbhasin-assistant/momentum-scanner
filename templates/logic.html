v3.8.0 Released 2026-07-06
TRADEABLE tier + anti-extension shadow fields — the three live-verified trading rules, in code. A 52-day full-history analysis (5,830 picks; 4,399 truly-live first-appearance picks 2026-05-12 → 07-06; bar-level enrichment of all 941 live STRONG picks; every claim independently re-derived by adversarial verification — see research_findings_live52d_elite_precision.md) reduced to three operator rules: (1) only trade STRONG in the opening 30 minutes; (2) of those, prefer the pick that hasn't already run; (3) enter immediately, never re-enter a stopped name. This release encodes rule 1 as a first-class TRADEABLE tier and rule 2 as persisted anti-extension shadow fields + an EXTENDED ⚠ warning badge; rule 3 was already live (SUPPRESS_REENTRIES) and is re-confirmed on live data (re-entries: 10.8% 2.5R-hit, −0.009R, n=343; only 9.6% of stopped STRONG losers ever print target later the same day). Tagged: added.

Why: On truly-live data the entire system edge lives in one corner: STRONG picks 09:30–10:00 ran +0.285 avgR / 25.8% 2.5R-hit (n=577) while STRONG 10:00–11:00 ran −0.123 avgR (n=221) and non-STRONG picks bled −100R across 3,458 picks. Within STRONG, the winners are the least-extended entries: mid-range fires (0.5–0.75 of the running day range) hit 34.9% / +0.55R vs 14.9% / +0.06R for top-of-range; 3+ consecutive green bars at signal = 12.5% hit, −0.09R. The composite score mechanically rewards extension, so the highest-scored pick is often the worst one on the board.

What changed (additive — no emission gating, no scoring change):

  • config.is_tradeable(signal) — single source of truth for TRADEABLE = STRONG AND entry inside [09:30, 10:00] ET inclusive. Constants TRADEABLE_ENABLED / TRADEABLE_WINDOW_START / TRADEABLE_WINDOW_END. ELITE is a strict subset of TRADEABLE. The shared window helper _signal_in_window now backs both the ELITE and TRADEABLE gates.
  • scanner.compute_extension_features(df) — look-ahead-safe features on the SAME reference bar as compute_strong_signal (most-recently-closed RTH bar): consec_green (green closed RTH bars ending at ref), range_pos (ref close position in the running RTH day range), above_orb_high (None until the 09:30–09:45 opening range is closed — no partial-OR peeking). Persisted per pick under extension.
  • config.is_anti_ext(signal) — tri-state shadow flag: True (pullback-quality: cg ≤ ANTIEXT_MAX_CONSEC_GREEN=2 and range_pos ≤ ANTIEXT_MAX_RANGE_POS=0.9), False (extended — the losing shape), None (features unavailable). SHADOW ONLY: never gates, never scores; collect ~4 weeks of live data before any promotion (adversarial verification showed the residual effect inside the catD+window control is modest: +1.3–6 hit-points).
  • Persistence: history.add_signals_to_daily slim record now carries elite (previously derived-on-read only), tradeable, anti_ext, extension — so future performance analysis reads the lived flags instead of reconstructing them from config constants.
  • Live dashboard (/) finally shows tier state — the signal cards previously displayed no STRONG/ELITE badges at all. New leading badges: cyan ELITE, green TRADEABLE, gold STRONG (shown only when outside the tradeable window, captioned "watch, don't chase"), dashed-red EXTENDED ⚠ with the consec-green / range-position values in the tooltip.
  • /today: green TRADEABLE pill + EXTENDED ⚠ pill in the Tier cell, data-tradeable row attribute, and a TRADEABLE only filter chip — three-way mutually exclusive with STRONG-only / ELITE-only (toggle logic refactored to a single spec-driven loop).
  • Sort priority in scanner.run_scan is now (elite, tradeable, strong, composite) descending.
  • Tests: tests/test_v38_tradeable.py — 17 cases covering window boundaries, ELITE⊂TRADEABLE, tri-state anti-ext, OR-close gating, pre-market exclusion from the running range, STRONG-reference-bar agreement, and slim-record persistence. Full suite: 33 passed.

Operator guidance (the three rules): act on TRADEABLE (and especially ELITE) picks only; between two simultaneous TRADEABLE picks take the one without the EXTENDED ⚠ badge; enter immediately (winners resolve in a median 60 min with 0.34R median adverse) and never revisit a stopped-out name.

v3.7.5 Released 2026-07-06
ELITE retightened on truly-live data; the 75.8% WR headline was a backfill artifact and is retired. A full-history audit of data/performance_log.json (5,830 picks, 52 sessions, 2026-04-20 → 07-06) found the strong_signal field did not exist in the persisted record until 2026-05-12 — every pick before that had STRONG reconstructed retroactively via /api/backfill_strong + strong_overrides.json. The old "19-day diagnostic, 75.8% WR" was computed almost entirely on that backfilled, look-ahead-contaminated window. On truly-live data ELITE ran 41.9% WR and decayed to 36.5% / +0.07R in the last month. Tagged: changed removed.

Why: The old ELITE rule (STRONG + cat=D + RVOL≥2) barely separates from plain STRONG live (38.6% vs 36.9% in June). The four strong_components (green bar, above-VWAP, new-HOD, PM-high-hold) are already all required for STRONG, so they can't act as an additional precision filter. The losers are not chased/extended moves; they are low-energy, tight-range setups that get stopped on noise. Sorted by stop distance: picks with stop < 0.75% of entry win 17–30%; picks with stop > 1.0% win 43–44%.

What changed — tightened ELITE rule (all gates on top of STRONG + cat=D):

  • RVOL band 2.0 ≤ rvol < 5.0 (ELITE_MIN_RVOL/ELITE_MAX_RVOL). The 5–6 RVOL band collapsed to 7% WR — blow-off/exhaustion prints.
  • RSI ≥ 68 (ELITE_MIN_RSI). The 60–70 band is dead (~36% WR); RSI 70–80 hit 43% WR, +0.29R.
  • Entry in the 09:30–10:00 ET window (ELITE_WINDOW_START/END). The 10:00–11:00 slot is a graveyard: 12.5% WR, −0.61R.
  • Stop distance ≥ 0.9% of entry (ELITE_MIN_STOP_PCT) — a volatility/energy floor so the 2.5R target is reachable before mean-reversion.
  • Single source of truth: new config.is_elite(signal) is the only place the rule lives. scanner.scan persists the boolean as signal["elite"]; notifier and all templates read that field instead of re-deriving (kills the rule-drift that let the flag live in five places). Legacy rule preserved behind ELITE_TIGHTEN_V375=False.

Verification: on live data 2026-06-01 → 07-06 the tightened rule lifts ELITE from 38.6% → ~49% WR and R/pick +0.12 → +0.50, keeping ~1/5 of picks (55 of 264). The discarded set netted near-zero R — edge removed cleanly. Out-of-sample on the last 15 sessions (6/15–7/06): 36.5% → ~48% WR. Honest caveat: on raw dollars the discarded set was +$181 (a few big EOD dollar movers with poor R), so this maximises risk-adjusted return / win rate, not absolute dollars.

Removed: the 75.8%/76% WR, +1.11%/pick, "profitable 16/17 days" claims from config.py, today.html, history.html, performance.html tooltips. Historical rows on /history retain their original label (no retroactive relabelling).

Rollback: set ELITE_TIGHTEN_V375=False in config.py → falls back to the legacy cat=D + RVOL≥2 rule (still without the retired WR claim).

v3.7.4 Released 2026-05-16 Superseded
Notifier now gates on ELITE-only, not Cat A/B + STRONG. The Resend email notifier previously fired on any STRONG pick that landed in Cat A or B (default since v3.5.8 / v3.7.0.2). v3.7.1 introduced the ELITE tier — STRONG + category=D + RVOL ≥ 2.0, 75.8% WR over 19 days. v3.7.4 makes that the default email gate: the notifier short-circuits the Cat A/B + STRONG-only filters and fires only when at least one ELITE pick is in the scan. The Cat A/B gate would have dropped every ELITE pick anyway (ELITE is by definition Cat D), so this isn't a stacked filter — it's a replacement. Tagged: changed.

Adding RVOL ≥ 2 raised that to 76% on the ~35% volume slice. The Cat A/B email gate was therefore actively selecting against the picks that work — sector leaders that wobble when SPY hiccups, vs idiosyncratic catalyst-driven breakouts that don't. The notifier had to be flipped to fix that.

What changed:

  • NOTIFY_ELITE_ONLY env var (default 1). When on, the notifier filter chain becomes: market-hours → strong-signal-strength → ELITE → min-signals → send. When off, falls back exactly to the v3.7.0.2 chain (Cat A/B + STRONG-only). Toggle without redeploy by flipping the variable in Railway's UI.
  • Cat A/B gate is now conditional, not always-on. Under NOTIFY_ELITE_ONLY=1 it is skipped entirely (running it over an ELITE-only list would always drop every pick, since every ELITE is Cat D). Under NOTIFY_ELITE_ONLY=0 it runs as before.
  • STRONG-only gate is also conditional. Same reason — every ELITE pick is by definition STRONG, so the gate is a no-op inside the ELITE path. Outside the ELITE path it runs as before.
  • Subject prefix unchanged. v3.7.1's [ELITE] prefix logic still applies: any ELITE pick in the surviving set → [ELITE], else [MScan]. Under the new default gate, every email by definition contains at least one ELITE pick, so the subject will read [ELITE] every time the notifier fires.

Volume expectation: 19-day diagnostic averaged ~3.5 ELITE picks/day; it fires on 17/19 days. So emails should drop from ~3–5 per day to roughly 1–2 per day (a single email per scan with all ELITE picks in it), with each email carrying picks that historically win 76% of the time.

Rollback: set NOTIFY_ELITE_ONLY=0 in Railway → falls back to v3.7.0.2 behaviour without a redeploy.

Verification: notifier.py compiles. The new _elite_only() helper mirrors _strong_only() exactly in env-var parsing. The conditional branch is set up so that under NOTIFY_ELITE_ONLY=1 the legacy Cat A/B + STRONG-only block is structurally unreachable; under NOTIFY_ELITE_ONLY=0 the legacy path runs identical to v3.7.3 (no behaviour change). v3.7.1 Released 2026-05-16
ELITE tier — a precision-refinement layer on top of STRONG. A pick is ELITE iff it is STRONG AND its post-hoc category is "D" (no sector-leadership classification — the idiosyncratic-breakout group) AND its RVOL is at or above 2.0. Pure post-hoc derivation, mirrored across scanner.py (sort priority), templates/today.html + templates/history.html + templates/performance.html (visual badge + filter chip), and notifier.py (subject prefix + row styling). No new field is persisted on the pick payload — every consumer derives the flag on read, so existing data/{date}.json and performance_log.json files Just Work.

Why. 19-day diagnostic over 188 STRONG picks (2026-04-20 → 2026-05-15) showed STRONG WR collapsed from 63% (pre-2026-05-14) to 50% on the last two live days as STRONG volume tripled. Root cause traced to two compounding effects: (1) pre-2026-05-12, compute_strong_signal silently no-op'd on every scan after 13:00 ET, so afternoon STRONG fires were structurally invisible; (2) 2026-05-14 was a continuation-day SPY tape (+0.79%, VIX 17.26) where the four-way conjunction fires ~2x more often. Both effects are real and they compounded. Within STRONG, the dominant precision driver was leadership category: category D = 72% WR vs LEADER/SOLO 50% vs LAGGARD 17% — idiosyncratic catalyst-driven breakouts outperform sector-beta breakouts that wobble when SPY hiccups. Adding RVOL ≥ 2 lifts WR to 76% on 35% of STRONG volume. Backed by 16/17 profitable days fired. Tagged: added.

What changed (additive — no breaking shape changes):

  • Three new config constants in config.py — ELITE_ENABLED (kill switch, default True), ELITE_REQUIRES_CATEGORY (default "D"), ELITE_MIN_RVOL (default 2.0). Tunable without redeploy if the rule needs revisiting.
  • Sort priority change in scanner.scan — final signal sort is now (elite, strong, composite_score) descending. ELITE picks float to the very top of /today; STRONG-but-not-ELITE picks sit below; the rest sort by composite score as before. MAX_SIGNALS_PER_SCAN cap unchanged.
  • ELITE badge in the Tier cell on /today and /history — cyan .tier-pill.elite chip, stacks alongside the existing gold STRONG chip (every ELITE pick is also STRONG). Row class becomes elite-row with a cyan left-edge accent that overrides the gold STRONG accent. Tooltip lists the rule and the 19-day WR.
  • ELITE-only filter chip on /today and /history and /performance — cyan chip alongside the existing STRONG-only chip. Mutually exclusive with STRONG-only — clicking one clears the other. /today count badge updates from the rendered DOM; /performance count updates inside the renderer as filters change.
  • Notifier visual treatment in notifier.py — subject is now [ELITE] N strong signals @ HH:MM — … when any pick in the batch is ELITE (otherwise the existing [MScan] prefix). ELITE picks in the HTML body get a 3px cyan left-border and a small ELITE tag next to the ticker. The Cat-A/B gate is unchanged — ELITE is purely a visual enhancement inside the existing email flow.
  • ELITE CSS in static/css/base.css — .tier-pill.elite (cyan), tr.elite-row (cyan left-edge), table.elite-only tbody tr[data-elite="0"] { display: none } (filter rule), .chip.elite-chip (toolbar chip).

Why no backfill of elite_signal: Every consumer (templates, notifier, scanner sort) derives ELITE on read from strong_signal + leadership.label + rvol — three fields already persisted on every pick row since v3.7.0. So /history pages render the ELITE badge correctly all the way back to the first day STRONG was computed (2026-04-22), no migration needed. If we ever want to persist the flag, the derivation rule is centralized in config so a one-shot script can add it without ambiguity.

Where to override behaviour:

  • Disable ELITE entirely: set config.ELITE_ENABLED = False — the sort key, the templates, and the notifier all early-exit.
  • Loosen the RVOL floor (more picks, less precision): drop config.ELITE_MIN_RVOL to 1.5 — projected 93 picks, ~72% WR per the 19-day curve. The TIGHT level.
  • Tighten further (fewer picks, more precision): raise to 3.0 — projected 43 picks, ~79% WR. The ULTRA level.

Verification: 19-day replay over data/performance_log.json (1,497 picks total, 188 STRONG): 66 ELITE picks, 75.8% WR, +1.11% avg per pick, +1.42R avg, profitable on 16 of 17 days it fired. Cross-checked: scanner.scan sort key now emits a 3-tuple; templates derive identical flag with the same threshold constants; notifier subject prefix and row styling switch on the same boolean. Diagnostic source: diagnostics_STRONG_2026-05-16.md.

The scan schedule was three overlapping cron jobs — the old :00/:30 momentum_scan plus separate :05 and :35 verification jobs — which double-fired (10:00 then 10:05, 10:30 then 10:35) and clustered scans 5 minutes apart. v3.7.0.19 Released 2026-05-14
Unified the live and backfill STRONG paths onto one bar-selection rule + per-session VWAP. Investigation of 2026-05-14 found the live STRONG path and the backfill path disagreed on 14 of 29 picks — they were evaluating bars one 5-min step apart. Two root causes, both fixed: (1) Bar offset. Live compute_strong_signal used df.iloc[-2] whenever the last row was a partial bar, which — when the scan ran a few minutes into a bar — reached back to the bar before the most-recently-closed one. Both compute_strong_signal and compute_strong_signal_at now share one helper (_most_recent_closed_rth_pos) that selects the most-recently-closed regular-hours bar as of a reference time, and one evaluator (_evaluate_strong_on_bar). compute_strong_signal gained a now_ref parameter so live and backfill resolve the identical bar for a pick found at the same clock time. (2) VWAP scope. calculate_indicators computed VWAP as a single cumsum() over the whole DataFrame — a 5-day rolling VWAP for the live path (5-day df) vs a true 1-day VWAP for the backfill path (1-day df). VWAP now resets per session day, so it is identical regardless of how many days of history are in the frame. Verified: post-fix, live and backfill agree on all 128 of 2026-05-14's picks (0 disagreements), and both correctly flag all six 2026-05-13 STRONGs under the current scan schedule. Note: this is a consistency fix — it does not change that 2026-05-14 STRONG win rate was ~17%, in line with that day's weak ~18% all-picks baseline. Tagged: fixed.

Sector Leadership Check v3.3

Sector Rotation tells us which sector is hot. Sector Leadership tells us whether this specific ticker is leading, following, or lagging its sector. The two complement each other: a stock can be in a hot sector but still be a laggard within it — and those laggards historically underperform even in favorable conditions.

How It Works

At scan time, the scanner compares three intraday % moves: the ticker's move since the open, its sector ETF's move, and SPY's move. The relative ordering produces a label:

LEADER (ticker% > sector% > SPY%) → ADMIT
SOLO MOVER (ticker > SPY, sector < SPY) → ADMIT
FOLLOWER (ticker > SPY, ≤ sector) → DROP
LAGGARD (ticker weaker than its sector) → DROP
UNKNOWN (sector ETF data unavailable) → DROP

Example: NVDA +2.1%  |  SMH +1.4%  |  SPY +0.5% → LEADER (admit)
Example: AMD +0.4%  |  SMH +1.4%  |  SPY +0.5% → LAGGARD (drop)

As of v3.3.2 this is a hard filter — only LEADER and SOLO MOVER candidates survive to the composite-score stage. The earlier +10/+3/−10 score adjustments are no longer added; admitted tickers must clear the raw min-score on their own technical merits. A 20-day backtest showed the score-boost approach was letting marginal-technical leaders through and causing disproportionate bleed during ELEVATED/HIGH VIX regimes.

Classification is skipped in the first 15 minutes after the open (before 9:45 AM) because early-session % moves are noisy and misleading — during this window all tickers come back UNKNOWN and are dropped.

Operators can override via config.LEADER_FILTER_MODE: "strict" (LEADER only), "moderate" (default, LEADER + SOLO), "permissive" (adds FOLLOWER), "score" (legacy boost-not-gate behaviour).

All 137 scanner tickers are now sector-mapped (v3.3.2), so "UNKNOWN" should only appear in the opening-15-min window or when yfinance is unavailable.

Rather than run the same aggressive scan in every environment, v3.3 reads ^VIX at each scan tick and tightens the bar dynamically.

Earnings announcements create discontinuous price jumps that ruin intraday stops — a stock can gap 10% through your stop overnight regardless of how strong the setup looked at 3:59 PM. v3.3 consults a locally-cached earnings calendar and both flags and, in the most dangerous case, blocks.

Pre-Market Catalyst Scan NEW

Runs at 8:00 AM and 9:00 AM ET, before the market opens. Checks up to 50 tickers for two signals:

1. Volume Ratio = Today's pre-market volume / Yesterday's full-day volume
  If > 2.0× → boost up to +10 pts (capped at 5× volume)

2. News Sentiment (via Finnhub + VADER)
  If sentiment > 0.3 → boost up to +10 pts

Combined boost capped at +15 pts per ticker.
Negative sentiment = no penalty, just no boost.

Critical design principle: This scan is purely additive. It boosts scores for pre-market movers but never prevents a stock from signaling if it only starts moving after the 9:30 AM open. A stock with no pre-market activity can still score 90+ on technicals alone.

News Sentiment Scoring (25% of score)

Headlines are scored using VADER (Valence Aware Dictionary for Sentiment Reasoning), enhanced with a finance-specific lexicon. Words like "bullish", "beat", "upgrade" get strong positive scores; "crash", "downgrade", "miss" get negative scores.

Recency Decay

Recent news matters more. A headline from 10 minutes ago gets full weight; one from 2 hours ago gets half weight.

Weighted Sentiment = Raw Score × Recency Weight

< 15 min old → 1.0× weight
15–30 min → 0.9×
30–60 min → 0.7×
1–2 hours → 0.5×
> 2 hours → 0.3×

First-Order vs. Second-Order Impact

First-order: Direct effect on the company in the headline. Apple beats earnings → Apple stock moves. This is scored directly from the headline.

Second-order: Spillover to related companies. Apple beats earnings → semiconductor suppliers (AVGO, QCOM) benefit from implied demand strength. The scanner tracks sector peer mappings and can flag when a peer has strong recent sentiment.

Data-Driven Filters NEW

These filters were derived from a 3-day backtest (159 trades, April 15–17, 2026). They remove statistically confirmed losing patterns:

Lunch Dead Zone (11:30 AM – 12:00 PM ET)

Scans scheduled at 11:30 and 12:00 are skipped entirely. In 3 days of data, lunch-hour batches produced 0 wins in 21 decided trades. The probability of this happening by chance (given the overall ~30% base win rate) is p < 0.001. Lunch-hour volume dries up and price moves during this window are unreliable.

Re-Entry Suppression

Each ticker can only generate one signal per day (its first appearance). Subsequent scans may detect the same ticker again, but these re-entries are logged and filtered out. In 3 days of data, re-entries produced 1 win in 32 decided trades (3.1% win rate). The pattern: by the time a stock appears a second time, the move has already happened — you're buying the top of a move that's running out of steam.

RVOL Exhaustion Penalty

When RVOL exceeds 5×, the volume component of the composite score is reduced by 30%. Extremely high volume — while attention-grabbing — often signals a climactic move or blow-off top rather than sustainable momentum. The penalty dampens (not eliminates) the signal.

Impact of Filters (3-day results)

Before filters: 159 trades, ~30% win rate
After filters: 85 trades, ~36% win rate

Dead zone removed: 21 trades (0 wins)
Re-entries removed: 32 trades (1 win)
Best time window: 1:00–3:00 PM ET (~67% win rate)

Pivot Point Resistance Levels

In addition to ATR-based targets, each signal includes the nearest Standard Floor Pivot resistance level above the entry price. This gives a Barchart-style overhead resistance estimate based on the prior day's price action.

Pivot (P) = (High + Low + Close) / 3

R1 = (2 × P) − Low
R2 = P + (High − Low)
R3 = High + 2 × (P − Low)

S1 = (2 × P) − High
S2 = P − (High − Low)
S3 = Low − 2 × (High − P)

The scanner finds the nearest R1, R2, or R3 above the current entry price and displays it as the Resistance Target (purple line on the chart). This helps you gauge how much room a trade has before hitting a natural ceiling.

Known Limitations

Data source failover: FMP is the primary data source for real-time quotes and 5-minute candles. If the FMP API is unreachable or returns errors, the scanner automatically falls back to yfinance (15-minute delayed data). During market hours, demo data is never shown — if both sources fail, the scan returns empty rather than stale prices.

FMP Starter plan limits: The Starter plan does not support batch-quote endpoints, so quotes are fetched one ticker at a time with rate limiting (4 calls/sec). A full scan of ~130 tickers takes ~30 seconds for quotes alone.

Filter sample size: Dead zone and re-entry filters are based on 3 days of data (159 trades). While statistically significant (p < 0.001 for dead zone), continued monitoring is important. The post-market analysis pipeline will accumulate more data to validate or refine these rules over time.

Sector rotation latency: Sector detection runs hourly (at :30 past each hour). A sudden sector rotation that happens at :45 won't be reflected until the next check at :30. The boost persists until the next detection run.

Pre-market data quality: Pre-market volume data from yfinance can be spotty for smaller-cap names. The scan limits to 50 tickers and uses the prepost=True flag, but coverage may vary.

History persistence: Daily finds are stored as JSON files on disk. On Railway (ephemeral filesystem), history is lost on redeploy. The trade log (scanner_trade_log.xlsx) is committed to the repo to survive redeployments.

News coverage: Finnhub free tier covers major headlines but may miss niche or breaking news. Sentiment scoring is keyword-based (VADER), not deep-learning. It catches obvious sentiment but may miss sarcasm or complex narratives.

Not financial advice: This scanner is an educational tool. Past technical patterns don't guarantee future results. Always do your own research and consider consulting a financial advisor.
